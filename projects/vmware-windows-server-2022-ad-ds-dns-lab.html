Lab Walkthrough

Phase 1 — Forest Root Domain Controller (DC1)

DC1 is the first server in the environment — the forest root domain controller that creates landonhotel.local and holds all five FSMO roles by default. The two-step process — install the AD DS role, then promote — is what transforms a plain Windows Server into the identity authority for the entire domain.

Step 1 — Role Installation

  • • AD DS role selected in Add Roles and Features wizard
  • • Group Policy Management and AD DS Tools added automatically as dependencies
  • • Auto-restart enabled before installation began
  • • Post-install: Server Manager shows "Configuration Required" — promotion not yet done

Step 2 — Promotion Wizard

  • • "Add a new forest" selected — no existing domain or forest yet
  • • Root domain name: landonhotel.local
  • • Forest and domain functional levels: Windows Server 2016
  • • DNS Server and Global Catalog enabled (required on first DC)
  • • DSRM password set and stored securely
  • • Prerequisites check passed — server rebooted into domain controller role

Domain Controller Options — Key Decisions

Setting Value / Reasoning
Forest Functional Level Windows Server 2016 — highest available; all DCs in this lab are Server 2022
DNS Server Enabled — AD DS requires DNS for all internal communication and service discovery
Global Catalog Forced on — first DC in any forest must be a GC; cannot be changed
RODC Unavailable — a writable DC must exist before any RODC can be added
Paths (NTDS, Logs, SYSVOL) Defaults accepted for lab; production should use separate physical drives

Post-Promotion Verification

After DC1 reboots, Server Manager shows AD DS and DNS under Roles. In ADUC (Tools → Active Directory Users and Computers), landonhotel.local appears with its default containers — Users, Computers, Domain Controllers, Builtin — confirming the domain is live.

Phase 2 — Additional Domain Controller (DC2)

A single DC is a single point of failure. DC2 joins the domain as a full writable domain controller, providing fault tolerance, load distribution, and full AD replication. The most common mistake — and the one most likely to fail the promotion — is not pointing DC2's DNS at DC1 before starting.

Pre-Promotion Requirements

  • • DC2 must have a static IP in the same network as DC1
  • • Preferred DNS server on DC2 must point to DC1's IP
  • • Without this, the wizard cannot locate landonhotel.local
  • • AD DS role installed via Add Roles and Features (same as DC1)

Promotion Wizard Differences

  • • "Add a domain controller to an existing domain" selected
  • • Domain admin credentials entered via Change — DC2's local admin has no domain authority
  • • DNS Server: enabled — best practice to have at least two DNS servers
  • • Global Catalog: enabled — improves performance in multi-domain forests
  • • Replication source: Any domain controller (recommended default)

Why Two DCs Are Non-Negotiable

Fault Tolerance

If DC1 fails, DC2 continues serving all authentication requests. Users keep working.

Redundancy

AD DS data replicates between all DCs — no single storage point for the directory database.

Load Distribution

Authentication requests spread across DCs. In larger environments, this meaningfully reduces latency.

Replication Options — Install from Media (IFM)

The promotion wizard offers three replication sources: any DC (default), a specific DC, or Install from Media. IFM is the important exception — when adding a DC to a remote location with poor WAN connectivity, a backup of an existing DC's database is exported to media and used to seed the new DC locally, avoiding large replication traffic across the WAN link. Not needed in this single-site lab, but a real scenario in multi-site enterprise deployments.

Phase 3 — Read-Only Domain Controller (DC3)

A Read-Only Domain Controller is built for one scenario: a remote or branch office that needs local authentication but has no dedicated IT staff to physically secure the server. An RODC provides full auth services while preventing any writes to the AD database — if it's physically compromised, the blast radius is limited to what's cached locally.

RODC Capabilities & Restrictions

  • • Provides full authentication services to local users
  • • Database is read-only — no changes can be written to AD
  • • Only caches passwords for explicitly allowed accounts
  • • Can be deployed as Server Core to reduce attack surface
  • • Supports a delegated local admin without granting domain admin rights

RODC-Specific Promotion Settings

  • • "Read Only Domain Controller" checkbox — the critical differentiator
  • • DNS and Global Catalog: typically left unchecked to minimize footprint
  • • Replication source: Any domain controller
  • • Password replication policy reviewed and configured

Password Replication Policy — The Critical RODC Config

This screen is unique to RODC promotion and has no equivalent elsewhere. It controls which passwords can be cached locally on the RODC — the decision that determines the scope of damage if the hardware is physically compromised.

Delegated Admin

A remote office user designated as local RODC admin — without domain admin rights. Your on-site contact for basic maintenance.

Allowed Replication

Remote office users whose passwords can be pre-cached locally. They can authenticate even if the WAN link to the main site goes down.

Denied Replication

Domain Admins, Schema Admins, and other privileged accounts. Always blocked — credentials for these accounts must never be stored on an RODC.

Phase 4 — Active Directory Management Tools

All AD management tools live under Server Manager → Tools. This phase walks through each one — what it's for, how it works, and when to use it. ADUC and ADAC are the daily drivers; the others cover infrastructure, sites, schema, and forensics.

Active Directory Users & Computers (ADUC)

Most widely used daily tool

The original AD tool — in use since Windows 2000. Classic tree view (left), content (right), right-click context menus for everything: create, delete, disable, reset password, move, properties.

Despite ADAC being newer, ADUC remains dominant because of familiarity and how AD knowledge has historically been taught and passed down.

Active Directory Administrative Center (ADAC)

PowerShell-backed modern tool

Built on PowerShell — every GUI click executes a cmdlet behind the scenes. Adds capabilities ADUC lacks: fine-grained password policies and the AD Recycle Bin.

ADAC's PowerShell History pane shows every command being run as you navigate the GUI — excellent for learning cmdlet equivalents of common tasks.

AD Domains & Trusts

Trust relationships & functional levels

Manages trust relationships between domains, raises domain and forest functional levels, and shows the Domain Naming Master FSMO role holder.

AD Sites & Services

Multi-site physical topology

Defines physical sites so users authenticate to the nearest DC — reduces WAN traffic and login latency. Manages subnets and inter-site replication transports (IP or SMTP).

Active Directory Schema (Custom MMC — Hidden by Default)

Forest blueprint — modify with extreme caution

The schema defines every object type (class) and every property (attribute) that can exist in AD. Modifications are forest-wide and irreversible. Microsoft hides this snap-in by default.

How to access the Schema snap-in

# 1. Register the DLL
regsvr32 schmmgmt.dll

# 2. Open a blank MMC
mmc

# 3. File → Add/Remove Snap-in → select Active Directory Schema → Add → OK
# Two nodes appear: Classes (object types) and Attributes (all properties)

Phase 5 — FSMO Roles & Command-Line Administration

FSMO roles are the five operations that cannot safely run on more than one DC at a time. All five default to DC1 in a new forest. Knowing where to find them — and how to move them when needed — is a core AD administration skill. This phase also covers DS command-line tools and the PowerShell AD module.

The Five FSMO Roles

Role Scope Function Where to Find It
Schema Master Forest Controls all schema updates AD Schema MMC → right-click root
Domain Naming Master Forest Ensures unique domain names in forest AD Domains & Trusts → right-click root
RID Master Domain Allocates RID pools for SID generation ADUC → right-click domain → Operations Masters → RID tab
PDC Emulator Domain Time sync, password changes, legacy support ADUC → right-click domain → Operations Masters → PDC tab
Infrastructure Master Domain Maintains cross-domain object references ADUC → right-click domain → Operations Masters → Infrastructure tab

All five roles held by DC1 by default. The PDC Emulator is the most operationally critical — it handles time sync and is first to receive password changes.

Transfer (Planned)

Current role holder is online. Gracefully move the role to another DC through the appropriate management tool. Use for planned maintenance or decommissioning.

Seize (Emergency)

Current role holder has permanently failed and cannot be recovered. Force another DC to take the role. The original DC cannot rejoin the domain afterward — seize only when recovery is off the table.

PowerShell & DS Command-Line Tools

The AD module for PowerShell is accessible directly from Server Manager → Tools and opens a PS window pre-loaded with AD cmdlets. The legacy DS tools (DSadd, DSget, DSmod, etc.) still work from a standard command prompt — primarily useful for legacy scripts.

PowerShell — Create & manage users

# Create and enable a new AD user
New-ADUser -Name "Jane Smith" `
           -SamAccountName "jane.smith" `
           -UserPrincipalName "jane.smith@landonhotel.local" `
           -AccountPassword (Read-Host -AsSecureString "Password") `
           -ChangePasswordAtLogon $true `
           -Enabled $true

# Add user to a group
Add-ADGroupMember -Identity "FrontDesk" `
                 -Members "jane.smith"

# Reset password
Set-ADAccountPassword -Identity "jane.smith" `
                      -Reset `
                      -NewPassword (Read-Host -AsSecureString)
Set-ADUser -Identity "jane.smith" `
           -ChangePasswordAtLogon $true

DS Command-Line Tools

# DSadd — create objects
DSadd user "CN=Jane Smith,OU=Staff,DC=landonhotel,DC=local"

# DSget — read properties
DSget user "CN=Jane Smith,OU=Staff,..." -memberof

# DSmod — modify attributes
DSmod user "CN=Jane Smith,OU=Staff,..." -disabled no

# DSquery — search objects
DSquery user -name "Jane*"

# DSmove — move between OUs
DSmove "CN=Jane Smith,CN=Users,DC=landonhotel,DC=local" `
       -newparent "OU=Staff,DC=landonhotel,DC=local"

# DSRM — remove objects
DSRM "CN=Jane Smith,OU=Staff,DC=landonhotel,DC=local"

PowerShell with the AD module is the preferred modern approach — better error handling, readable syntax, and pipeline support. DS tools remain valid for legacy scripts.

Tier 1 — Infrastructure Foundations

Get the fundamentals right before anything else.

  • Always deploy two DCs minimumOne DC is a single point of failure. Two is the baseline for any production environment, regardless of size.
  • Static IPs before AD DS installationDynamic addressing causes DNS and replication failures. Set static IPs and verify connectivity first.
  • Point new DCs at existing DC for DNSDC2 and DC3 must resolve the domain via DC1's DNS before promotion — missing this is the most common failure.

Tier 2 — Security & Access

Protect the identity plane from the start.

  • Store DSRM passwords securelyThe Directory Services Restore Mode password is needed for DC recovery — cannot be reset through normal means.
  • Never put privileged accounts in RODC allowed replicationDomain Admin, Schema Admin credentials must never cache on an RODC — physical compromise exposes them.
  • Treat schema modifications as irreversibleSchema changes apply forest-wide and permanently. Never experiment on production; always document and plan.

Tier 3 — Operational Excellence

Build repeatable, resilient habits.

  • Separate storage for NTDS, logs, SYSVOLIn production, each component on its own physical drive significantly improves AD performance and resilience.
  • Use AD-integrated DNS zonesZones stored inside the AD database replicate to all DCs automatically — more resilient than standalone DNS zones.
  • Automate with PowerShellScripted provisioning and deprovisioning reduces human error, speeds onboarding, and creates an auditable record.

What I Learned

Key takeaways

  • • Promoting a DC is always two steps — role install, then promotion wizard — and order matters
  • • DNS configuration before promotion is the single most common failure point when adding DCs
  • • RODC password replication policy is not optional — it's the core of what makes an RODC safe to deploy remotely
  • • ADUC and ADAC accomplish the same daily tasks — ADAC is only required for fine-grained passwords and the Recycle Bin
  • • All five FSMO roles live in three different tools — knowing where to look is part of the job
  • • PowerShell through ADAC's history pane is one of the best ways to learn AD cmdlets in context
