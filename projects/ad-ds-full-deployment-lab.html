Phase 0 — VM Provisioning

Before any AD role gets installed, three Windows Server 2022 VMs need to exist. Each needs a name, hardware allocation, and a static IP. This phase is the foundation everything else depends on — and the reason DC2 and DC3 will fail promotion if you skip the DNS configuration step.

Pre-lab requirement: Each VM needs a static IP before any AD DS installation begins. DC2 and DC3 must also have their Preferred DNS set to DC1's IP — not their own, not a public DNS server. Without this, the promotion wizard cannot locate landonhotel.local and the whole process fails.

Phase 1 — Forest Root DC (DC1)

DC1 becomes the forest root domain controller — the first DC in the forest, holder of all five FSMO roles by default, and the DNS authority for landonhotel.local. Promoting it is always two steps: install the role, then run the promotion wizard. They are separate operations.

Phase 2 — Additional DC (DC2)

A single DC is a single point of failure. DC2 joins as a full writable domain controller — providing fault tolerance, redundancy, and load distribution. The role install is identical to DC1. The promotion wizard is different in one critical way: instead of creating a new forest, you join an existing domain. And DC2 must be pointing at DC1 for DNS before any of this starts.

Pre-Promotion
Configure DC2 before touching the wizard
DC2 needs a static IP and Preferred DNS set to DC1's IP. This is the step most people skip — and the one that causes the failure shown below.
DC2 Local Server — verify static IP + DNS before promotion
DC2 — AD DS role installed, promotion pending
Real Failure — Documented
DNS misconfiguration causes promotion to fail
The promotion wizard cannot locate landonhotel.local because DC2's DNS was still pointing at the wrong server. This is the most common DC promotion failure in the field. The fix is straightforward: open the network adapter, change Preferred DNS to DC1's IP, restart the wizard.
⚠ Promotion fails — wizard cannot find landonhotel.local (DNS misconfigured)
Error: "The specified domain either does not exist or could not be contacted."
Fix: Network Adapter → IPv4 → Preferred DNS = DC1's IP. Run the wizard again.
Why it happens: The local admin account DC2 is using can't resolve the domain. Domain credentials entered via "Change" in the wizard won't help if DNS can't locate the domain first.
After the Fix
DC2 promoted successfully — full writable DC
With DNS corrected, promotion completes. DC2 joins landonhotel.local as a full writable DC with DNS and Global Catalog. Replication with DC1 begins automatically. The environment now has fault tolerance — if DC1 goes down, DC2 continues serving authentication.
DC2 Server Manager — AD DS role active, full writable DC confirmed

Phase 3 — Read-Only DC (DC3 / RODC)

An RODC is for one specific scenario: a remote or branch office that needs local authentication but has no dedicated IT staff to physically secure the server. A standard writable DC in an unsecured location is a serious risk — physical access means credential hash extraction. An RODC can't be written to, and only caches passwords for explicitly allowed accounts. The blast radius of a physical compromise is limited to what's cached locally.

Critical Promotion Screen
Password Replication Policy — RODC only
This screen doesn't exist for standard DC promotions. It controls which accounts can have passwords cached on the RODC — the decision that determines how much damage a physical compromise can cause.
✓
Allowed: Remote office users whose passwords can be pre-cached. They can auth locally if WAN goes down.
✗
Always denied: Domain Admins, Schema Admins, all privileged groups. These must never cache on an RODC.
△
Delegated admin: A non-domain-admin user can be designated as local RODC admin for the branch office.
Never put Domain Admin or Schema Admin in the Allowed list. If the RODC is physically compromised, those cached credentials are fully exposed.

AD Sites & Services — multi-site topology
Sites & Services — DemoSite creation for branch office scenario

Sites represent physical locations. This tool routes users to authenticate against the nearest DC — reducing WAN traffic and login latency. Subnets are mapped to sites so new computers are automatically assigned to the right site when they join the domain.

Lab note: DemoSite was created for illustration purposes only. Moving DCs between sites in production without careful planning breaks authentication routing and replication scheduling.

Phase 5 — FSMO Roles

AD uses multi-master replication — any writable DC can accept changes. But five operations can't safely run on more than one DC at a time. For those, a single DC holds the role. All five start on DC1. This phase covers locating them, transferring them (planned), and seizing them (emergency).

Step 2 — Transfer (Planned)
Gracefully move RID Master from DC1 to DC2
Transfer is used when the current role holder is online and available. You initiate it through the management tool — the old DC gracefully hands off the role. Used for planned maintenance, DC decommissioning, or load redistribution.
1 — Transfer preparation initiated from DC1
2 — RID Master transferred to DC2, confirmed
3 — PDC Emulator error (expected — tool still querying old holder)
Final transfer confirmation dialog — DC2 now holds RID Master
PDC Emulator error is expected: The tool was still pointing at the old role holder. Refreshing the connection or reconnecting to DC2 resolves it immediately. Not a real failure.
Step 3 — Seize (Emergency via NTDSUTIL)
Force Domain Naming Master to DC2 — role holder permanently offline
Seize is the emergency procedure when the current role holder has permanently failed and cannot be recovered. You use NTDSUTIL from the command line to force the role to another DC. The original role holder cannot rejoin the domain afterward — seize only when recovery is completely off the table.
NTDSUTIL → FSMO maintenance menu
NTDSUTIL → connecting to DC2 for seizure
NTDSUTIL → FSMO role management console
Domain Naming Master seized on DC2 — emergency takeover confirmed
Seize is a last resort. Once you seize a role, the original holder must never come back online in the domain. If it does, you'll have two DCs both believing they hold the same FSMO role — which causes serious directory corruption. Seize only after confirming permanent failure.

Reference & Best Practices

Tier 1 — Infrastructure
Two DCs minimum, always

One DC is a single point of failure. Two is the production baseline regardless of org size.

Static IPs before installation

Dynamic addressing causes DNS and replication failures. Verify connectivity first.

DNS before promotion

DC2 and DC3 must point at DC1 for DNS before the wizard starts — the most common failure if skipped.

Tier 2 — Security
Store DSRM passwords securely

Needed for DC recovery, cannot be reset normally. Lose it and you lose your recovery path.

Never cache privileged creds on RODC

Domain Admins must never be in the RODC allowed replication list. Physical compromise exposes cached credentials.

Schema changes are irreversible

Forest-wide and permanent. Never experiment on production.

Tier 3 — Operations
Separate NTDS, logs, SYSVOL storage

Each on its own physical drive in production. Significantly improves performance and resilience.

AD-integrated DNS zones

Stored inside AD, replicated to all DCs automatically. More resilient than standalone DNS.

Automate with PowerShell

Scripted provisioning reduces error, speeds onboarding, creates an auditable record.
