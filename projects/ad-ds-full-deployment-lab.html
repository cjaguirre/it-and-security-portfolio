DC Deployment Walkthrough

DC1 — Forest Root Domain Controller

DC1 is the first domain controller in the forest — the Forest Root DC. Installing AD DS here creates the entire landonhotel.local forest from scratch. Every other DC in the lab joins after this one exists. It always holds all five FSMO roles by default.

Two-step process

Step 1 — Install the AD DS role
Server Manager → Add Roles and Features → Active Directory Domain Services. Accept all required feature dependencies. Auto-restart checkbox enabled. Installation completes but the server is not yet a DC — Server Manager shows "Configuration Required."
Step 2 — Promote to domain controller
Click "Promote this server to a domain controller" from the notification flag. Select Add a new forest, enter landonhotel.local as the root domain name. This is the only option available before any domain exists.

DC Options — what each setting means

Setting
Decision
Forest Functional Level
Windows Server 2016 — highest available. Controls feature compatibility with older DCs.
DNS Server
Enabled. AD DS requires DNS. Best practice: co-locate DNS on at least one DC.
Global Catalog
Checked and grayed out — mandatory. The first DC in any forest must be a GC server.
RODC
Unavailable. A RODC requires a master writable DC to already exist.
DSRM Password
Directory Services Restore Mode — used to boot into recovery if AD fails. Store securely.

Database paths (production vs lab)

Production: The NTDS database, transaction log files, and SYSVOL should live on separate physical drives — not just different folders on the same disk. Separating I/O across drives significantly improves performance and resilience.
This lab: Default paths accepted — C:\Windows\NTDS for the database and logs, C:\Windows\SYSVOL for the shared folder.

Verifying DC1 after reboot

After the promotion wizard completes, the server reboots automatically. Log back in as LANDONHOTEL\Administrator. Server Manager now shows AD DS and DNS listed under Roles. Go to Tools → Active Directory Users and Computers to confirm landonhotel.local exists with its default containers: Users, Computers, Domain Controllers, Builtin.

DC2 — Additional Domain Controller

Regardless of company size, a minimum of two domain controllers is always recommended. If DC1 fails, DC2 continues serving authentication — users stay logged in, resources stay accessible, and the domain remains operational. DC2 is a full writable replica of the directory.

Fault Tolerance

If one DC fails, the other continues authenticating users with no service interruption.

Redundancy

AD DS data is replicated between all DCs — no single point of failure for the directory database.

Load Balancing

Authentication requests can be distributed across DCs, reducing load on any single server.

Critical pre-promotion check

Most common mistake: DC2's DNS must point to DC1 before promotion. If DC2 can't resolve landonhotel.local through DC1's DNS, the Configuration Wizard will fail to find the domain. Set DC2's Preferred DNS Server to DC1's IP address in the network adapter settings first.

Deployment configuration differences

  • • Select "Add a domain controller to an existing domain" — not a new forest
  • • Enter landonhotel.local and click Change to provide domain admin credentials
  • • DC2's local admin account has no authority over the domain — explicit domain credentials required
  • • Enable DNS Server and Global Catalog — same as DC1
  • • Replication source: leave as "Any domain controller" — wizard picks the best available
Install from Media (IFM): When deploying a DC in a remote location with a slow WAN link, you can export a backup of an existing DC's database to media, then seed the new DC from that local copy instead of replicating across the WAN. Not needed in this single-site lab, but important in multi-site enterprise deployments.

DC3 — Read-Only Domain Controller (RODC)

An RODC is designed for branch offices or remote sites where there is no dedicated IT staff to physically protect the domain controller. The security risk with a standard writable DC is real: an attacker with physical access can extract credential hashes or modify AD objects. An RODC limits the blast radius — no writes can be made to the directory, and only explicitly allowed account passwords are ever cached locally.

RODC provides

  • • Full authentication services to local users
  • • Password caching only for explicitly allowed accounts
  • • Can be deployed as Server Core to reduce attack surface
  • • Delegated admin — a non-admin user can manage the RODC locally without domain admin rights

RODC restrictions

  • • No changes can be written to AD — the database is read-only
  • • Privileged accounts (Domain Admins, Schema Admins) are denied caching by default — must stay denied
  • • If physically compromised, only cached passwords are exposed
  • • No changes originate from the RODC — it only receives replication

RODC-specific promotion steps

  • • Check Read Only Domain Controller (RODC) box — this is the key distinction
  • • DNS Server and Global Catalog left unchecked — minimal footprint for the branch
  • • Password Replication Policy screen appears — unique to RODC promotion
Never add Domain Admin, Schema Admin, or other privileged account passwords to the Allowed Replication list. If the RODC is physically compromised, those cached credentials become immediately exposed.

Password Replication Policy

This screen is unique to RODC deployment and controls which accounts can cache passwords locally. Accounts in the "Allowed RODC Password Replication Group" can authenticate even if the WAN link to the main site goes down.

Allowed Replication

Add the security group containing remote office users so they can authenticate locally during WAN outages. Add custom groups via the Add button. These passwords are pre-seeded on the RODC.

Denied Replication (Defaults)

Domain Admins, Schema Admins, Enterprise Admins, and other privileged groups are blocked by default. These entries must remain denied — remove none of them.

AD Users & Computers vs. AD Administrative Center

These are the two primary GUI tools for day-to-day AD management. Both accomplish the same standard tasks. ADAC is the newer, more powerful tool — but ADUC remains the most widely used because most administrators learned on it and it handles everything needed for routine work.

AD Users and Computers (ADUC)

  • • Classic GUI since Windows 2000 — Explorer-style tree navigation
  • • Right-click context menus for all object operations: Create, Delete, Disable, Reset Password, Move
  • • Multi-tab Properties window (General, Account, Profile, Member Of, etc.)
  • • Used to find FSMO roles: right-click domain → Operations Masters
  • • Domain Controllers container confirms DC list including DC3 RODC

AD Administrative Center (ADAC)

  • • Built on PowerShell — every GUI action executes a cmdlet behind the scenes
  • • PowerShell History pane shows commands in real time — excellent for learning PowerShell equivalents
  • • Fine-Grained Password Policies — different complexity rules for specific groups (not possible in ADUC)
  • • AD Recycle Bin — recover deleted objects without a backup restore (requires WS2008 R2+ forest level)
  • • Breadcrumb navigation history — fast switching between frequently visited containers
No wrong answer: ADUC and ADAC accomplish the same standard AD management functions. ADAC is required only for fine-grained password policies and the AD Recycle Bin — everything else can be done in either tool.

AD Sites and Services

Sites in AD represent physical locations connected by WAN links. The Sites and Services tool defines this topology so users authenticate to the closest domain controller — improving login speed and eliminating unnecessary WAN traffic. Critical in multi-location enterprises.

Sites

Physical locations and the servers assigned to them. All three DCs start in Default-First-Site-Name.

Subnets

IP ranges mapped to each site. When a new computer joins the domain, its IP determines its site automatically.

Inter-Site Transports

Controls replication between sites: IP (most common, uses RPC) or SMTP (for unreliable connections).

Lab demonstration: creating a new site

  1. Right-click Sites → New Site, name it DemoSite (no spaces in site names)
  2. Assign a site link — required to create the site
  3. Move a DC: navigate to Default-First-Site-Name → Servers, drag a DC to DemoSite
  4. Confirmation warning appears — the move is complete
Production warning: Do not move DCs between sites without planning. Incorrect site assignments affect authentication routing, replication scheduling, and WAN efficiency. This was demonstration only — DCs were moved back after.

AD Schema — The Hidden Tool

The AD Schema is the master blueprint of the entire directory — the definition of every object class (User, Computer, Group, OrgUnit) and every attribute they can have. Modifying the schema changes the structure of the entire forest, permanently and irreversibly. Microsoft hides this tool by default to prevent accidental access.

Treat as irreversible: Schema changes are forest-wide and permanent. In production, they are almost always made automatically by enterprise software (Exchange, System Center, SCCM) — never by hand. Never experiment on a production AD schema.

How to access the Schema snap-in

# Step 1: Register the schema DLL
regsvr32 schmmgmt.dll
# Success dialog: "DllRegisterServer succeeded"

# Step 2: Open a blank MMC
mmc

# Step 3: File → Add/Remove Snap-in
# Active Directory Schema is now available in the list
# Add it, then save the MMC for future use:
# File → Save As → Windows Administrative Tools → "Active Directory Schema"
Saving the MMC to Administrative Tools makes it accessible from Server Manager's Tools menu in the future — no need to re-register the DLL.

What the Schema snap-in shows

Classes

Every object type defined in AD: User, Computer, Group, OrgUnit, Contact, and more. Each class has a set of mandatory and optional attributes.

Attributes

Hundreds of properties that can be assigned to objects — everything from mail and telephoneNumber to objectGUID and userAccountControl.

Command-Line Tools — DS Utilities & PowerShell

GUI tools are efficient for individual operations. Scripts handle scale. The DS command-line utilities predate PowerShell but are still valid for legacy scripts. PowerShell is the modern, preferred approach for automating AD operations — better error handling, readable syntax, and pipeline support.

DS command-line utilities (CMD)

Command
What it does

Add new objects — supports user, computer, group, OU, contact, quota
DSget

PowerShell AD module — common helpdesk tasks

# Create and enable a new domain user
New-ADUser -Name "John Doe" `
           -SamAccountName "john.doe" `
           -UserPrincipalName "john.doe@landonhotel.local" `
           -AccountPassword (Read-Host -AsSecureString "Password") `
           -ChangePasswordAtLogon $true `
           -Enabled $true

# Add user to a security group
Add-ADGroupMember -Identity "HotelStaff" `
                 -Members "john.doe"

# Reset password, force change at next login
Set-ADAccountPassword -Identity "john.doe" `
                      -Reset `
                      -NewPassword (Read-Host -AsSecureString)
Set-ADUser -Identity "john.doe" `
           -ChangePasswordAtLogon $true

# Unlock a locked-out account
Unlock-ADAccount -Identity "john.doe"

# Disable an account on offboarding
Disable-ADAccount -Identity "john.doe"
ADAC + PowerShell history: While working in the AD Administrative Center, the PowerShell History pane at the bottom displays every cmdlet being executed as you click through the GUI. This is the fastest way to learn AD PowerShell — do it in the GUI, read what the tool actually ran, then start scripting it yourself.

FSMO Roles

Active Directory uses multi-master replication — all writable DCs hold an equal copy of the database and changes can be made on any of them. But certain operations can't safely run on multiple DCs simultaneously. For those, AD designates a single authority: the FSMO role holder. There are five roles total — two forest-wide, three domain-wide.

FSMO Role
Scope
Function
Schema Master
Forest
Controls all updates to the AD schema. Only one per forest — ever.
Domain Naming Master
Forest
Ensures domain names are unique when adding or removing domains from the forest.
RID Master
Domain
Manages the pool of Relative IDs allocated to other DCs for generating object SIDs.
PDC Emulator
Domain
Time synchronization for all domain members, password changes, legacy pre-Windows 2000 client support. Most operationally critical role day-to-day.
Infrastructure Master
Domain
Maintains consistency of cross-domain object references, such as group memberships referencing users in other domains.

Finding all 5 FSMO roles — 3 different tools

ADUC → Domain → Operations Masters

Right-click landonhotel.local → Operations Masters. Three tabs appear — one per domain-level role.

  • • RID — RID Master
  • • PDC — PDC Emulator
  • • Infrastructure — Infrastructure Master

All three show DC1 as the current holder in this lab.

AD Domains & Trusts → Root → Operations Master

Right-click the root node "Active Directory Domains and Trusts" (not the domain name itself). Select Operations Master.

  • • Domain Naming Master — one role shown

DC1 is the Domain Naming Master holder.

AD Schema (Custom MMC) → Operations Master

Register schmmgmt.dll, open a blank MMC, add the Schema snap-in. Right-click "Active Directory Schema" → Operations Master.

  • • Schema Master — one role shown

DC1 is the Schema Master holder.

PDC Emulator is the most critical: It handles time synchronization for all domain members and is the first DC to receive password changes. An out-of-sync clock (more than 5 minutes) breaks Kerberos authentication entirely — making this role the highest operational priority.
Transfer vs. Seize: If the role holder is online, transfer gracefully through the tools above. If it has permanently failed, seize by forcing another DC to take the role — but the original role holder cannot rejoin the domain afterward. Seize only when recovery is impossible.

What I Learned

Key takeaways

  • • AD DS is the central identity platform for any Windows enterprise — authentication, access control, and policy all flow through it
  • • DC promotion is always two steps: install the role, then run the Configuration Wizard — they are separate operations
  • • DNS is not optional — Active Directory cannot function without it, which is why co-locating DNS on domain controllers is best practice
  • • A minimum of two domain controllers is always required — one DC is a single point of failure for the entire environment
  • • RODC design is specifically about limiting physical breach impact — not just convenience for remote sites
  • • FSMO roles are spread across three separate tools — you have to know where to look for each one
  • • The AD Schema should be treated as untouchable in production — changes are forest-wide, permanent, and irreversible
  • • ADAC's PowerShell history pane is the fastest way to bridge GUI knowledge into scripted administration
