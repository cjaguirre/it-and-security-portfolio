Phase 0 — VM Provisioning

Before any AD role gets installed, three Windows Server 2022 VMs need to exist with names, hardware, and static IP addresses. This is also where the DNS prerequisite matters most — DC2 and DC3 must point at DC1 for DNS before promotion starts, or the wizard fails.

Critical pre-lab step: Every VM needs a static IP before any AD DS installation begins. DC2 and DC3 must also have their Preferred DNS pointed at DC1's IP — not their own, not a public server. Skipping this causes the most common DC promotion failure in the entire lab.

Phase 1 — Forest Root DC (DC1)

DC1 becomes the forest root domain controller — the first DC in the forest, the authority for landonhotel.local, and the default holder of all five FSMO roles. Promotion is always two separate steps: install the role, then run the promotion wizard.

Step 1 of 2 — Install the role
Add Roles and Features → Active Directory Domain Services
Server Manager → Add Roles and Features. Select Active Directory Domain Services. Dependencies (Group Policy Management, AD DS Tools) are added automatically. Check auto-restart, install. After completion, Server Manager shows "Configuration Required" — expected. The binaries are installed but the server hasn't been promoted yet. That's Step 2.
Add Roles and Features wizard — AD DS selected, dependencies auto-added
Step 2 of 2 — Promote to Forest Root DC
AD DS Configuration Wizard — "Add a new forest"
Click "Promote this server to a domain controller" from the notification flag. Select Add a new forest, enter landonhotel.local. Set functional levels to Windows Server 2016. DNS and Global Catalog are enabled (required on the first DC — GC is forced on and cannot be changed). Set a DSRM password. Run prerequisites check. Install. Server reboots into its new role.

Phase 2 — Additional DC (DC2)

A single DC is a single point of failure. DC2 joins as a full writable DC, providing fault tolerance and replication. The role install is identical to DC1. The promotion wizard is different — instead of creating a new forest, you join an existing domain using domain admin credentials. But first, DC2's DNS must be pointed at DC1. That step got skipped.

Real failure — documented
DNS misconfiguration causes promotion to fail
The promotion wizard cannot locate landonhotel.local because DC2's Preferred DNS was still pointing at the wrong address. The wizard fails immediately with a connectivity error. This is the most common DC promotion mistake in the field — and it's easy to avoid with one pre-check.
⚠ Promotion fails — "The specified domain could not be contacted." DNS not pointed at DC1.
Error: "The specified domain either does not exist or could not be contacted."
Fix: Network Adapter → IPv4 → Preferred DNS = DC1's IP address. Run the wizard again.
After the fix
DC2 promoted successfully — full writable DC
With DNS corrected, the wizard finds the domain, accepts the domain admin credentials entered via Change, and completes promotion. DC2 joins landonhotel.local as a full writable DC with DNS and Global Catalog. Replication with DC1 begins automatically. The environment now has fault tolerance — if DC1 fails, DC2 continues handling authentication.
DC2 Server Manager — AD DS role active, full writable DC confirmed in the domain
Why two DCs are non-negotiable
Fault tolerance

If DC1 fails, DC2 keeps serving auth. Users stay logged in and resources stay accessible.

Redundancy

AD data replicates between all DCs. No single storage point for the directory database.

IFM for remote sites

When adding a DC over a slow WAN link, Install from Media seeds the new DC from a backup — no replication traffic.

Phase 3 — Read-Only DC (DC3 / RODC)

An RODC is for a specific scenario: a branch office that needs local authentication but has no dedicated IT staff to physically protect the server. If someone gains physical access to a standard writable DC, they can extract credential hashes for every account in the domain. An RODC can't be written to, and only caches passwords for accounts you explicitly allow — limiting the blast radius of a breach.

Before and after domain join
DC3 starts as a standalone server, joins as RODC
Same process as DC2 to start: static IP, DNS pointed at DC1, AD DS role installed. The difference comes in the promotion wizard — one checkbox separates this from a standard DC.
DC3 — standalone server, pre-join state. No domain, no roles yet.
DC3 — RODC successfully joined to landonhotel.local
The critical promotion screen
Password Replication Policy — unique to RODC
This screen doesn't exist for standard DC promotions. It controls which accounts can have passwords cached locally on the RODC. Accounts in the Allowed list can authenticate locally even if the WAN link to the main site goes down. Accounts in the Denied list — Domain Admins, Schema Admins — must never cache here. If the RODC hardware is physically stolen or compromised, only cached credentials are exposed.
RODC promotion wizard — "Read Only Domain Controller" checkbox checked, password replication policy configured
Never add Domain Admin or Schema Admin to the Allowed replication list. If the RODC is physically compromised, those cached credentials are fully exposed. Privileged accounts must always remain in the Denied list.

Delegation is one of the most practically relevant AD concepts for helpdesk work. Instead of giving a team lead Domain Admin rights just to reset passwords, you delegate only the reset password permission on a specific OU. They can reset passwords for their team — nothing else, nothing broader.

Phase 5 — FSMO Roles

AD uses multi-master replication — any writable DC can accept changes. But five operations can't safely run on more than one DC at a time. For those, a single DC is designated the master. All five start on DC1. This phase covers locating them, transferring them when planned, and seizing them in an emergency.

Find all five holders — they live in three different tools

Transfer — planned move
RID Master transferred from DC1 to DC2
Transfer is used when the current role holder is online. You initiate it through the management tool and the role is handed off gracefully. Use this for planned maintenance or decommissioning. The original DC stays functional.
Transfer preparation — initiating the move from DC1 to DC2
RID Master successfully transferred to DC2 — confirmation dialog
PDC Emulator error immediately after transfer — the tool was still pointing at the old role holder. Expected behavior, not a real failure.
The error is expected: The management console was still connected to DC1 when the role moved to DC2. Refreshing the connection or reconnecting to DC2 resolves it immediately.
Seize — emergency via NTDSUTIL
Domain Naming Master seized — role holder permanently offline
Seize is the last resort. Used only when the current role holder has permanently failed and cannot be recovered. You force another DC to take the role via NTDSUTIL. The original holder cannot rejoin the domain afterward — seize only when recovery is completely off the table.
NTDSUTIL → FSMO maintenance → role management console — the command-line path to seizure
Domain Naming Master seized on DC2 — confirmed. The original holder can no longer rejoin the domain.
Seize is destructive and irreversible. Once seized, if the original role holder comes back online in the domain, you'll have two DCs both believing they hold the same FSMO role — causing serious directory corruption. Only seize after confirming permanent, unrecoverable failure.

Reference & Best Practices

Tier 1 — Infrastructure
Two DCs minimum, always

One DC is a single point of failure. Two is the baseline regardless of organization size.

Static IPs before installation

Dynamic addressing breaks DNS and replication. Verify static IPs before touching any role.

DNS before promotion

DC2 and DC3 must point at DC1 for DNS before the wizard starts. Skipping this causes the failure shown in Phase 2.

Tier 2 — Security
Store DSRM passwords securely

Needed for DC recovery, cannot be reset through normal means. Lose it and you lose your recovery path.

Never cache privileged creds on RODC

Domain Admins must stay in the Denied list on every RODC. Physical compromise exposes cached credentials.

Schema changes are irreversible

Forest-wide and permanent. Test environments only. Never experiment in production schema.

Tier 3 — Operations
Separate NTDS, logs, SYSVOL

Each on its own physical drive in production. Defaults accepted in this lab.

AD-integrated DNS zones

Stored inside AD, replicate to all DCs automatically. More resilient than standalone zones.

Delegate, don't over-privilege

Give helpdesk exactly the permissions they need. Delegation exists so you never have to hand out Domain Admin rights.
